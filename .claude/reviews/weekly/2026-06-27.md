## 1. Duplicações 🟡
- **33 arquivos** formatam data/`dayKey` manualmente com `padLeft(2,'0')`. Já
  existe a fonte canônica `core/time/nexago_event_timezone.dart` (`nexagoEventDayKey`)
  — oportunidade de migrar os 33 sites e eliminar risco de divergência de fuso.
- **8 definições** locais de `formatCurrency`/`formatMoney`/`formatBRL`.
- **7 definições** locais de `_formatDate/_formatTime/_formatHour`.
→ Faltam utilitários de formatação centralizados em `core/` (moeda, data, hora).

## 3. Controllers / classes gigantes 🟡
- `functions/src/index.ts` — **3.093 linhas**, com **31 triggers definidos inline**
  (não é só agregador de re-exports). É o god-file do backend; dificulta cold-start,
  leitura e teste. Extrair os triggers inline para módulos por domínio.
- `tournament-partner-invite.ts` (1175) e `organizer-match-ops.ts` (950) também grandes.
- App: `gamification_service.dart` (847, 15 métodos), `booking_service.dart` (812)
  concentram muita responsabilidade.

## 4. Violações SOLID / arquitetura 🔴
- **Violação clara de camada**: `auth/domain/role_selection_providers.dart` importa
  `arena/presentation/widgets/arena_selection_gate.dart` — domain → presentation **e**
  acoplamento cruzado entre features (auth ↔ arena). Corrigir.
- **Padrão sistêmico**: **53 arquivos** de `domain/` importam `data/`. Sob a
  convenção real (providers vivem em `domain`) isso é pragmático, mas **contradiz a
  Clean Architecture documentada** em `.claude/CLAUDE.md`.
- **Documentação x realidade divergem**: o `.claude/CLAUDE.md` define camadas
  `presentation/application/domain/infrastructure`; a estrutura real é
  `presentation/domain/data` (sem `application`/`infrastructure`). Além disso:
  `home/` não tem subcamadas e `auth/` tem `widgets/` solto na raiz da feature.
  → Decidir: atualizar o documento para a arquitetura real **ou** convergir o código.

## 5. Arquivos desnecessários / deps 🟢
- Sem `.bak/.old/copy/tmp` no código-fonte. Os únicos hits estão em
  `nexago_app/build/` (artefato gerado) — **verificar se `build/` está no
  `.gitignore`** para não vazar artefatos no repo.
- Sem dependências mortas no `pubspec`. Nenhum segredo hardcoded.

## 6. Dependências circulares 🟡
- Sem ciclos óbvios `data↔presentation`. O risco está no acoplamento cruzado
  entre features (item 4) — auth dependendo de arena cria potencial de ciclo futuro.

## 7. Testabilidade 🟡
- ~138 testes para 1.000 arquivos. A lógica de domínio pura (ex.: `ScheduleLogic`,
  `tournament_group_standings_logic`) está bem coberta — esse é o caminho certo.
- Gargalo: as páginas gigantes (item 2) misturam UI + lógica, dificultando testes.
  Functions têm só ~6 arquivos de teste para 105 de código.

## 8. Performance 🟡
- **90** usos de `.snapshots()` vs **46** `.limit(` — há streams/queries sem teto.
  Em coleções que crescem (matches, inscriptions, rankings) isso aumenta leituras
  e custo do Firestore. Auditar streams sem `limit`/paginação.
- **70** `ListView(` não-builder vs **54** `ListView.builder/.separated/SliverList`.
  Listas dinâmicas longas sem virtualização pesam no scroll.
- (Da revisão diária) N+1 sequencial em `notifyBracketPublishedAthletes`.

## 9. UX 🟢/🟡
- i18n consistente (PT). Sem strings de UI em inglês.
- Páginas muito densas (item 2) tendem a ter navegação/scroll pesados — revisar
  hierarquia visual das maiores (registration, profile, slots).

## 10. Segurança 🟡
- **23 coleções com `allow read: if true`** (leitura pública total). A maioria é
  legítima (tournaments, leagues, arenas, courts, rankings, reviews, slots). **Auditar
  PII/sensibilidade** especialmente em:
  - `artifacts/.../inscriptions/{registrationId}` — inscrições podem conter dados
    pessoais/pagamento.
  - `auditLog/{eventId}` — log de auditoria com leitura pública pode vazar operações.
  - `pointEvents/{eventId}` — eventos de gamificação por usuário.
- Sem segredos no código. Webhooks de pagamento usam HMAC/`timingSafeEqual` (bom sinal).
